# 北通手柄 HID 协议规格

> 本文描述 betop-battery 所依赖的帧格式与命令。
> 内容来自**互操作性分析**（观察官方客户端的通信行为），不含任何厂商代码。
> 目标是让你能自己为**其它北通型号**写出设备描述文件。

## 1. 传输层

- 使用 **HID**（人机接口设备）通信，跨平台通过 `hidapi` 访问
- 一个北通接收器会枚举出**多个 HID 接口**（复合设备），典型如下：

| 接口 | usage_page / usage | 用途 |
|---|---|---|
| ① | `0xFF00` / 任意 | ⭐ **厂商自定义接口 —— 状态查询走这里** |
| ② | `0x0001` / `0x0002` | 鼠标模拟 |
| ③ | `0x0001` / `0x0006` | 键盘模拟 |
| ④ | `0x0001` / `0x0005` | 手柄本体（XInput 呈现） |

**关键**：厂商接口的存在是判断"能不能读到电量"的依据。
如果某型号的厂商接口不存在或没有响应，可能需要换连接方式（如蓝牙模式）。

## 2. 帧格式

所有帧（收/发）都是同样的结构：

```
+-----------+-----------+---------------------------+
| report_id |  header   |         payload           |
|  1 byte   |  1 byte   |         N bytes           |
+-----------+-----------+---------------------------+
```

**header 字节拆成两个 4 位字段**：

```
  bit:  7  6  5  4 | 3  2  1  0
        └── subcmd ─┘└─── cmd ──┘

  header = (subcmd << 4) | cmd
```

Python 里就是：

```python
header = (subcmd << 4) | cmd          # 打包
cmd, subcmd = header & 0x0F, header >> 4   # 拆包
```

> 这与官方客户端脚本中的 `data.substr(n*2, 2)` 一一对应：
> **`n` 就是本文使用的"整帧偏移"**（0 = report_id，1 = header，2 起是 payload）。

## 3. 命令表

### 已知命令

| cmd | subcmd | header | 含义 | 方向 |
|---|---|---|---|---|
| `0x5` | `0x1` | **`0x15`** | **状态报告（含电量、充电状态）** | 请求 / 上报 |
| `0x5` | `0x2` | `0x25` | 按键/摇杆报告 | 持续上报 |
| `0x5` | `0x5` | `0x55` | 固件版本信息 | 请求 / 上报 |
| `0x2` | `0x1` | `0x12` | 读配置 | 请求 / 上报 |
| `0x2` | `0x2` | `0x22` | 写配置 | 请求 |

> ⚠️ 本工具**只发送读类命令**（`cmd=0x5`），**不发送写配置命令**。

### 请求状态报告（读电量）

发送 **2 字节**即可（其余补零到报告长度）：

```
02 15
│  └── header 0x15 = 状态报告
└───── report_id（鲲鹏20 为 0x02）
```

**写入长度敏感**：某些固件要求写满报告长度（如 64 字节）。因此实现里会依次尝试
`64 → 32 → 16`，描述文件中的 `write_lengths` 可覆盖这个顺序。

## 4. 状态报告（header `0x15`）的字段

鲲鹏20 实测帧：

```
02 15 64 00 51 01 01 00 00 00 00 00 00 00 00 00 ...
│  │  │  │  │  │  │  └── byte[7]
│  │  │  │  │  │  └───── byte[6]
│  │  │  │  │  └──────── byte[5]
│  │  │  │  └─────────── byte[4] 低4位 → 充电状态（非0=充电中）
│  │  │  └────────────── byte[3]
│  │  └───────────────── byte[2] → 电量百分比（0~100 十进制）
│  └──────────────────── header
└─────────────────────── report_id
```

| 整帧偏移 | 位宽 | 含义 | 说明 |
|---|---|---|---|
| `byte[2]` | 8 | **电量** | 直接是 0~100 的十进制值（`0x64` = 100）|
| `byte[4]` 低 4 位 | 4 | **充电状态** | `0` = 用电池，非 `0` = 充电中 |
| `byte[7..8]` | 16 | 面板信息 | 小端 |
| `byte[9..10]` | 16 | 面板掩码 | 小端 |

> 其它型号**很可能只有偏移和 report_id 不同**，字段语义一致（同一协议家族）。

## 5. 为什么标准 API 读不到

很多现成工具（XInputBatteryMeter、Windows GameInput 等）之所以读不到，
是因为接收器在与 Windows 的标准通道上**把自己报告为"有线设备"**：

```
XInputGetBatteryInformation() → BatteryType = WIRED, BatteryLevel = FULL
```

这**不代表真的满电**，只是"不通过标准通道上报"。所以必须像本工具这样
**直接与厂商接口通信**。

## 6. 调试清单（遇到读不到时）

| 现象 | 排查方向 |
|---|---|
| 找不到设备 | 接收器是否插好；手柄是否休眠（按一下按键） |
| 打不开接口 | 官方客户端是否独占（关掉试试）；换个 `--iface` |
| 写不进去 | 调整 `write_lengths`（试 64 / 32 / 16 / 33） |
| 收不到响应 | header 是否对（用 `probe scan` 试一组）；接口是否选对 |
| 电量值不对 | 偏移错了，或需要 `scale`（如 0~255 → 0~100 用 0.3922） |
| 充电状态不对 | 用 `mask` 取正确的位 |

## 7. 协议家族参考

官方客户端内置了多个型号的脚本（命名类似 `kp20d` / `kp40b` / `kp70` / `t9` 等），
它们共享本文描述的同一套帧结构。因此适配新型号的一般流程是：

1. 用 `probe` 找出该型号的 `report_id` 与状态查询 header（通常就是 `0x15`）
2. 用 `probe watch` 在充/放电时对比，定位电量与充电状态字节
3. 写入描述 JSON
